# Реестр командных веток

Версия: 2026-09-21. Репозиторий: https://github.com/DanK1-PRO/Hakaton-2026.git, private.

Этот файл фиксирует, какая ветка кому принадлежит и для чего она создана. Он нужен Даниилу и AI-агентам участников, чтобы не путать экспериментальные ветки с готовыми PR.

Все найденные стыки между ветками фиксируются отдельно в `docs/team/INTEGRATION_STITCHES.ru.md`. Перед финальным прогоном на Astra этот журнал нужно вывести Даниилу целиком и принять решение по каждому пункту.

## Правила для всех веток

- `main` считается стабильной рабочей версией.
- Участники работают в своих ветках и открывают Pull Request в `main`.
- Ветка может существовать как тестовая, но это не значит, что ее можно merge.
- Перед PR ветка должна быть обновлена от свежего `origin/main`.
- Если ветка меняет API, схемы, БД, Docker, workflow или ML-контракт, Даниил должен проверить это отдельно.
- Если GitHub Actions красный, PR не сливать.
- Если при проверке веток найден стык, конфликт тестов, конфликт скриншотов, пересечение API/ML/UI-контракта или спорная зона ответственности, добавить запись в `docs/team/INTEGRATION_STITCHES.ru.md`.

## Текущее замечание по ветке Максима

`ml/scoring-experiment` сейчас полезна как тест подключения и черновик evaluator service. Перед merge нужно:

1. Обновить ветку от `origin/main`.
2. Убрать trailing whitespace.
3. Пометить скоринг и формулы сложности как `TEAM_PROPOSAL` / experimental, а не как официальную шкалу заказчика.
4. Не подключать `data_derived/scenarios/classifier_scenarios.json` как истину сценариев без отдельного ревью.
5. Проверить, что `ML_MODE=mock` не сломан.

## Текущее замечание по ветке Сани

`ui/sanya-results-admin` выглядит аккуратно по зоне: списки, результаты, админка, тесты и docs/images. Перед финальным merge с веткой Даниила нужно заменить проверку `frontend/tests/flow.spec.ts:149` на локатор нового ARM service dock или статус из API, потому что `.workspace-heading` больше не является частью карточки.

## Как обновлять этот реестр

При появлении новой ветки добавлять строку в таблицу с владельцем, направлением и статусом. Если ветка стала неактуальной, не удалять запись сразу: сначала пометить как `closed`, `merged` или `abandoned`, чтобы история команды оставалась понятной.
