# Мастер-ТЗ UI-команды: Даниил, Никита, Саня

Версия: 2026-09-20. Репозиторий: https://github.com/DanK1-PRO/Hakaton-2026.git, private.

Этот документ нужен как входное ТЗ для людей и для их AI-агентов. Он фиксирует, где UI-команда может работать свободно, где требуется согласование, и как не сломать интеграцию с backend/ML-командой.

## 1. Текущая база

В репозитории уже есть рабочая версия `v0.1.0`:

- React 18 + TypeScript + Ant Design + Redux Toolkit.
- FastAPI + PostgreSQL 15 + Alembic.
- Русский интерфейс тренажера ДДС.
- Авторизация по ролям: обучающийся, преподаватель, администратор.
- Карточки происшествий, сценарии, учебный телефон, история действий, результаты.
- ML подключается через mock/local gateway, React напрямую к ML не обращается.
- GitHub Actions проверяет backend, frontend, браузерные тесты и Docker Compose.

Перед началом любой задачи AI-агент участника должен прочитать:

1. `AGENTS.md`
2. `docs/ai/PROJECT_STATE.md`
3. `docs/VERIFICATION.md`
4. `docs/PROJECT_MAP.md`
5. этот файл

Для UI-задач также читать:

1. `docs/ui/SCREEN_MAP.md`
2. `docs/ui/UI_COMPONENT_INVENTORY.md`
3. `docs/ui/UI_BEHAVIOR.md`
4. `docs/ui/UI_SOURCE_MAP.md`

## 2. Главная цель UI-команды

Пока Кирилл и Максим подключают реальные ML-модели, UI-команда доводит интерфейс до уверенного демонстрационного состояния без изменения базовой архитектуры.

Цель: сделать русский интерфейс тренажера удобным, плавным, устойчивым и готовым к подключению реальных ML-результатов через уже существующий API.

Важное ограничение: UI-команда не переписывает backend, БД, ML gateway и контракты данных без согласования с Даниилом и Кириллом/Максимом.

## 3. Распределение ответственности

### Даниил

Владелец вертикальной интеграции и приемки:

- Следит, чтобы UI не расходился с источниками заказчика.
- Принимает изменения в рабочем месте диспетчера.
- Проверяет, что после изменений проходят тесты и Docker/Windows запуск.
- Согласует изменения API-контрактов с Кириллом и Максимом.
- Обновляет документацию, если поведение экрана реально изменилось.

Основные файлы Даниила:

- `docs/team/*`
- `docs/ui/*`
- `docs/ai/*`
- `docs/VERIFICATION.md`
- `docs/CURRENT_STATUS.md`
- `frontend/src/workspace.tsx`
- `frontend/src/types.ts`
- `frontend/tests/flow.spec.ts`

### Никита

Рекомендуемая зона: рабочее место диспетчера и карточка происшествия.

Можно работать:

- `frontend/src/workspace.tsx`
- `frontend/src/components.tsx`
- `frontend/src/styles.css`
- `frontend/tests/flow.spec.ts`
- `docs/ui/UI_BEHAVIOR.md`
- `docs/ui/SCREEN_MAP.md`

Типовые задачи:

- Улучшить эргономику карточки вызова.
- Довести мобильную и desktop-адаптацию.
- Улучшить отображение истории действий.
- Сделать понятнее состояния вызова, приема, отказа, реагирования и завершения.
- Добавить аккуратные loading/error/empty состояния.

Нельзя без согласования:

- Менять названия API-полей.
- Менять порядок жизненных состояний карточки.
- Отключать проверку версии карточки.
- Делать React-запросы напрямую к ML-сервису.

### Саня

Рекомендуемая зона: списки, результаты, кабинет преподавателя/администратора, демонстрационные экраны.

Можно работать:

- `frontend/src/pages.tsx`
- `frontend/src/results.tsx`
- `frontend/src/App.tsx`
- `frontend/src/components.tsx`
- `frontend/src/styles.css`
- `frontend/tests/flow.spec.ts`
- `docs/DEMO.md`
- `docs/USER_GUIDE.md`

Типовые задачи:

- Улучшить таблицы, фильтры, поиск и сортировки.
- Доработать кабинет преподавателя и просмотр результатов.
- Доработать admin-экран создания пользователей.
- Улучшить демо-маршрут показа проекта.
- Проверить, что интерфейс понятен без устного объяснения.

Нельзя без согласования:

- Убирать существующие сценарии и результаты.
- Переписывать авторизацию.
- Менять формат CSV без обновления тестов и документации.

## 5. UI-инварианты

Эти правила нельзя ломать:

- Весь пользовательский интерфейс на русском языке.
- React работает только через FastAPI API, без прямых вызовов ML.
- Обучающийся видит сценарий и карточку, но не скрытые эталонные ответы.
- Преподаватель видит результаты и может оставить обратную связь.
- Администратор может создавать пользователей, но не должен получать скрытые ML-ручки в UI.
- Терминальная карточка не редактируется после завершения или отказа.
- Если версия карточки устарела, UI должен показать конфликт или обновиться корректно.
- Ошибка ML не должна ломать прохождение тренировки: система показывает fallback-результат.
- Мобильная ширина около 390 px не должна иметь глобальный горизонтальный скролл.

## 6. Главные UI-массивы и состояния

Работать нужно через существующие типы в `frontend/src/types.ts`.

Ключевые массивы:

- `IncidentType[]`: справочник типов происшествий из классификатора.
- `Scenario[]`: учебные сценарии.
- `Incident[]`: карточки происшествий.
- `ActionEvent[]`: история действий по карточке/сессии.
- `TrainingSession[]`: тренировочные сессии.
- `EvaluationResult`: результат mock/local/fallback оценки.
- `InstructorFeedback[]`: обратная связь преподавателя.

Ключевые состояния карточки:

- `received`
- `accepted`
- `rejected`
- `responding`
- `arrived`
- `working`
- `completed`
- `refused`

UI может улучшать визуализацию этих состояний, но не должен менять их смысл.

## 7. Рекомендуемые UI-задачи на ближайший этап

1. Провести ручной UX-проход по роли обучающегося: вход, сценарий, звонок, заполнение карточки, реагирование, завершение, просмотр результата.
2. Улучшить экран карточки: плотность, читаемость, группы полей, ошибки, состояния загрузки.
3. Доработать списки происшествий: быстрый поиск, понятные фильтры, устойчивый вид на mobile.
4. Доработать результаты: отделить автоматическую оценку от комментария преподавателя.
5. Уточнить демо-сценарий для показа заказчику: какие экраны открывать и в каком порядке.
6. Обновить browser-тесты под измененный UI.
7. Проверить `npm run build` и Playwright перед PR.

## 8. Правила GitHub-работы

Основная ветка: `main`.

Нельзя пушить напрямую в `main`, если работа ведется командой. Делать ветки:

- `ui/danil-workspace-polish`
- `ui/nikita-card-flow`
- `ui/sanya-results-admin`
- `docs/team-spec-update`

Перед PR:

1. Синхронизироваться с `origin/main`.
2. Запустить локально минимум:

```powershell
cd frontend
npm run build
npx playwright test
```

Если затронут backend или API:

```powershell
.\.venv\Scripts\python.exe -m pytest backend\tests
.\.venv\Scripts\python.exe -m ruff check backend ml scripts
```

3. В PR написать:

- Что изменено.
- Какие экраны затронуты.
- Какие проверки пройдены.
- Менялись ли API/схемы/данные.

4. Не мерджить PR, если GitHub Actions красный.

## 9. Конфликты с ML-командой

UI-команда должна ожидать, что Кирилл и Максим будут менять только ML-сервис и, возможно, предлагать расширение контрактов.

Если ML-команде нужно новое поле на экране:

1. Они описывают поле в русском и английском ML-ТЗ.
2. Даниил решает, является ли поле частью UI или внутренним ML-параметром.
3. Если поле нужно в API, меняются `backend/app/schemas.py`, `config/*.schema.json`, тесты и документация.
4. Только после этого UI добавляет отображение.

UI не должен заранее добавлять случайные ML-поля "на будущее". Неизвестные будущие улучшения остаются в документации, а не в интерфейсе.

## 10. Готовность UI-задачи

Задача считается готовой, если:

- UI работает на desktop и mobile.
- Нет глобального горизонтального скролла на 390 px.
- Русские тексты не обрезаются в кнопках и таблицах.
- Сохраняется прохождение полного учебного сценария.
- Не сломаны роли.
- `npm run build` проходит.
- Playwright проходит или в PR явно указано, почему тест временно не может пройти.
- Документация обновлена, если пользовательский сценарий изменился.
